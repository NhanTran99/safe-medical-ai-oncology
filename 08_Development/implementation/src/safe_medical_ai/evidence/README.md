# Runtime Evidence Package Boundary (Task #005)

## What this is

The controlled transformation boundary between the Retrieval Layer and a
future Generation layer, per the locked architecture:

```text
Navigation Context
        ↓
Retrieval Layer
        ↓
Retrieval Result (RetrievalResponse)
        ↓
RTEP Assembly                       (this module)
        ↓
Immutable Runtime Evidence Package
        ↓
Generation                          (not implemented — future task)
```

`RetrievalResponse` (Task #003) and `RuntimeEvidencePackage` are distinct
contracts (B1-03) — this module assembles the latter from the former plus
caller-supplied runtime metadata/provenance. It does not implement
Generation or Output Validation.

## Interfaces

- **`RuntimeEvidencePackage`** — the immutable RTEP: `metadata`
  (`RuntimeEvidenceMetadata`) + `evidence` (an immutable `tuple[EvidenceItem, ...]`,
  never a mutable `list`).
- **`RuntimeEvidenceMetadata`** — `evidence_package_id`, `retrieval_id`,
  `navigation_context_id`, `retrieval_policy_version`, `knowledge_base_version`,
  `generation_timestamp` (`EVIDENCE_PACKAGE_SPECIFICATION.md` §7 / spec §5.2).
  `evidence_package_id` and `generation_timestamp` are generated by assembly
  itself; the other four come from the caller-supplied `RTEPAssemblyContext`
  (spec §10 explicitly allows identity/timestamp fields to be
  runtime-generated while everything else stays deterministic).
- **`EvidenceItem`** — one retrieved Clinical Knowledge Object reference
  (`population_id`, `artifact_type`, `source_path`, `title`, carried forward
  unchanged from the originating `RetrievalCandidate`) plus its
  `EvidenceItemProvenance`. Contains no prompt instructions, prompt
  templates, model directives, or generated content (§5.4).
- **`EvidenceItemProvenance`** — `knowledge_object_id`, `knowledge_passport_id`,
  `source_id`, `guideline_version` (`EVIDENCE_PACKAGE_SPECIFICATION.md` §8 /
  spec §5.3). Supplied by the caller via `provenance` (see below), never
  derived or invented by assembly.
- **`RTEPAssemblyContext`** — the caller-supplied runtime metadata assembly
  needs but cannot itself know (`retrieval_id`, `navigation_context_id`,
  `retrieval_policy_version`, `knowledge_base_version`). Pass `None` if
  unavailable.
- **`RTEPAssemblyOutcome`** — `ASSEMBLED` / `RETRIEVAL_NOT_FOUND` /
  `RETRIEVAL_INVALID_REQUEST` / `MISSING_METADATA` / `INVALID_EVIDENCE_ITEM` /
  `INCOMPLETE_PROVENANCE`. A distinct vocabulary from both `RetrievalOutcome`
  and OUTPUT_CONTRACT's `ValidationOutcome` (spec §14) — never merged with
  either.
- **`RTEPAssemblyResult`** — the atomic result of one assembly call:
  `outcome`, `package` (`None` unless `outcome == ASSEMBLED`), the echoed
  `request`, and an optional `message`.
- **`assemble_runtime_evidence_package(retrieval_response, *, context, provenance=None)`**
  — the one explicit, testable assembly boundary (B4-05). `provenance` is a
  `Sequence[EvidenceItemProvenance]` **positionally parallel** to
  `retrieval_response.results` — item `i` belongs to candidate `i`.

### Why provenance is positional, not keyed by `source_path` (Change Request RC-01)

The first implementation keyed a `provenance_by_source_path` mapping by
`RetrievalCandidate.source_path`. Review correctly identified that the
locked retrieval contract (Task #003/#004) never establishes `source_path`
as a unique evidence identity — two distinct candidates may legitimately
share one. A `source_path`-keyed mapping would then make provenance
ambiguous for duplicates: both would resolve to whichever entry occupied
that key. Association is now strictly positional (index-parallel to
`retrieval_response.results`), which keeps every candidate's provenance
unambiguously one-to-one regardless of `source_path` duplication — see
`test_duplicate_source_paths_retain_unambiguous_distinct_provenance` in
`test_evidence_assembly.py`. A provenance-sequence length mismatch against
`retrieval_response.results` is itself an atomic `INCOMPLETE_PROVENANCE`
failure (missing or excess entries both rejected).

## Why there's no `AMBIGUOUS` outcome

Spec §14 lists `AMBIGUOUS` as a retrieval-originated outcome "where
applicable." It is not applicable here: the locked, preserved
`RetrievalOutcome` contract (Task #003/#004) has no ambiguous state of its
own — `FilesystemRepositorySource` already resolves an ambiguous population
match to `NOT_FOUND` rather than surfacing ambiguity upward. Adding a dead,
unreachable `AMBIGUOUS` value to `RTEPAssemblyOutcome` would be a
speculative abstraction with no code path that could ever produce it, so it
was deliberately omitted.

## Assembly semantics

| Input `RetrievalResponse.outcome` | `context` | Every candidate has provenance? | Result |
|---|---|---|---|
| `NOT_FOUND` | — | — | `RETRIEVAL_NOT_FOUND`, no package |
| `INVALID_REQUEST` | — | — | `RETRIEVAL_INVALID_REQUEST`, no package |
| `FOUND` / `EMPTY` | `None` | — | `MISSING_METADATA`, no package |
| `FOUND` / `EMPTY` | present | any candidate malformed (blank `source_path`/`population_id`) | `INVALID_EVIDENCE_ITEM`, no package |
| `FOUND` / `EMPTY` | present | `provenance` length doesn't match `results` length | `INCOMPLETE_PROVENANCE`, no package |
| `EMPTY` | present | (no candidates to check) | `ASSEMBLED`, empty-but-valid RTEP |
| `FOUND` | present | yes, lengths match | `ASSEMBLED`, complete RTEP |

Assembly is atomic (B3-11): any failure path returns immediately with
`package=None` — never a partial package built from whichever candidates
happened to succeed first.

Evidence ordering is exactly `retrieval_response.results`'s order — assembly
never sorts, reranks, or deduplicates (spec §11; behaviorally tested,
including that duplicate `source_path` candidates are preserved rather than
collapsed).

## Not implemented by this task (deferred / out of scope)

- Generation, Output Validation, and everything downstream of RTEP.
- Loading actual artifact text content: `RetrievalCandidate` (Task #003/#004)
  carries only structural pointers (`source_path`, `title`), not file
  content, so `EvidenceItem` carries the same — there is nothing to load.
- A real source of `EvidenceItemProvenance` / `RTEPAssemblyContext` values
  (e.g. reading the Knowledge Asset Registry / Population Integration
  Manifest at runtime) — this module only consumes whatever the caller
  supplies; it does not fetch or derive provenance itself.
- Embeddings, vector database/engine, semantic retrieval, LLM provider/model,
  prompt generation, clinical reasoning.
